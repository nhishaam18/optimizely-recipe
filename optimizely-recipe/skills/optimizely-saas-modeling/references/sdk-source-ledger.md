## Conflicts resolved or explicitly deferred

1. **SDK field flags:** earlier bundle examples used `required`/`localized`. In 1.3.0 SDK examples use the inspected declarations' `isRequired`/`isLocalized`. Mapper source does not rename incorrect aliases. Pair type checking with manifest assertions and real editor validation.
2. **REST field flags:** CMS web type docs and tutorials conflict, and the CLI's vendored OpenAPI uses `isRequired`/`isLocalized`. The inherited direct-REST examples use `required`/`localized` and remain **unverified illustrative payloads**, not the new code-first contract. Resolve against the selected tenant API/schema/readback before sending direct REST; do not silently translate or send both. Prefer the qualified CLI serialization path for this iteration.
3. **Application updates:** the SDK content guide still recommends delete/recreate, while inspected implementation PATCHes updates. Use version-qualified updates; do not follow the destructive workaround.
4. **Config generation:** the fresh/scaffold template uses a `buildConfig` subpath whose inspected target has only type definitions, whereas Stride/Alloy import the function from the SDK root. Its `manifest push` script also differs from `config push` for `.mjs`. Inspect actual generated package output and help before adopting it.
5. **Rich-text presets/defaults:** source declares `default`, `expanded`, `minimal`; prose refers to `standard` in places. Use installed declarations, with `minimal` in the example. Verify JSON selection when rendering SDK RichText; do not combine an HTML-only sample with a JSON-only query.
6. **Template maturity:** Stride marks itself work in progress and contains placeholders. Raw templates have workspace package references and cannot be assumed standalone. Published scaffold qualification is still required.

The [shared glossary](common/cms-glossary.md), [code-first recipe](saas/code-first-modeling.md) and [sample walkthrough](../../optimizely-nextjs/references/template-patterns.md) explain how to apply these findings. Older PaaS references remain historical, excluded from this SaaS implementation path.

## 1.3.6 compatibility and validation boundary

The source baseline above remains 3.0.0-beta.0. No 2.x compatibility claim is added. [Supported modeling contract](supported-model-contract.md) records option placement, array definitions, ownership and mismatch handling. [Validation](model-validation.md) distinguishes profile preflight from full schema/CMS acceptance. The bundled profile checks generated properties against this inspected subset; it is not a vendored complete OpenAPI schema. Documentation/SDK conflicts require the selected project's evidence, not routine lookup during component startup.

The reported `isList` failure is one example of unknown options surviving compile-time checks. A corrected declaration needs regenerated output, constraint preservation and validation; casting or deleting editorial constraints is not a fix. Concrete unresolved model/manifest/CMS errors now permit the same narrow recovery as compiler errors.


Component localization safeguard: on a property with type `component`, omit `isLocalized` entirely, including false. Apply approved localization to supported individual fields on the referenced component type; do not blanket-localize every child or alter shared consumers without reviewing their semantics. Component array items also cannot carry this metadata. Keep valid array-container metadata distinct from item metadata, and do not apply this prohibition to `contentReference` or scalar properties. Include the choice in each component handoff. During Phase 2 write definitions/examples in the handoff only; application changes belong to authorized implementation. Check the generated manifest with the scoped preflight before any separately authorized tenant sync. Do not initiate a push or routine SDK lookup to check this rule. TypeScript success and preflight success do not prove full CMS acceptance.
