# Implementation-only entry

Required gate: this reference applies only to an explicit authorized implementation task. Phase 2 documentation, model examples and handoff preparation never activate first-edit behavior. Follow [operation contract](operation-contract.md); retain the current task mode on continuation.
Use when the user asks to implement from supplied model/discovery artifacts, says earlier phases are complete, or resumes an implementation task. Start at phase 3 for the named scope. For a new migration without a usable design, use the normal discovery path. This entry changes local execution order; it does not certify earlier phases or authorize tenant writes. For a renderer-only correction with an unchanged approved model, reuse that model and start the affected renderer edit/check; model creation steps below apply only when needed.

## First actions

1. **Read the assigned component, foundation or page-assembly document once.** It is the sole mandatory handoff read. Repository instructions still apply. Open shared definitions only at the exact heading named for the current edit. Original full handoff, index and approval records are provenance/reference only; consult them only for a specific contradiction or missing requirement. Copy approval provenance into the component document rather than re-reading it at startup. Extract the selected slice, stable keys, fields, ownership, composition and existing authorization. The latest explicit user decisions govern changed scope; preserve unaffected decisions. A filename containing `simulation` does not override a later instruction to implement local code. Ask only about a concrete conflict that changes the next model; implement unaffected units meanwhile.
2. **Check execution mode and repository.** If runtime plan mode prohibits edits, submit the existing bounded implementation plan through its real exit mechanism immediately and wait for the required decision. Reuse an accepted exit; do not start another design cycle. In execution mode, inspect repository instructions, user changes, package manifest/lockfile, one existing model/renderer and its registration/discovery paths in one targeted read batch. Preserve user changes and the installed SDK family.
3. **Reuse the supplied SDK pattern.** Reuse the component handoff and existing model/renderer pattern. Do not read or search node_modules, SDK source/tests/source maps or external SDK documentation before initial implementation, through file tools or shell commands. Missing qualification is not a reason for broad investigation. Report a specific unresolved modeling conflict and continue independent work. New-project setup or explicitly assigned SDK investigation is a separate scope.
4. **Write the first required source change now.** Using the supplied pattern, the next action is a source edit for one approved semantic unit (or the assigned foundation/assembly change) (and only its required dependencies), followed by the existing local type-check command. Add the renderer, registration, discovery glob and local fixture/route; run focused checks. If tooling is missing, attempt a concrete supported repair, record an unrun check honestly, and continue independent source work. Missing credentials do not prevent model or UI files.
5. **Review the manifest after code exists.** Generate/review it against the actual exports and approved design before any tenant synchronization. If CLI dry run authenticates and credentials are absent, use supported local extraction if available; otherwise record manifest generation blocked and continue renderer/local verification. Never describe a type check as manifest or tenant validation. Tenant diff/readback, application/content/locale operations, publication, deployment and independent editorial QA keep their existing authorization and evidence gates.

The first implementation deliverable is an actual required model or renderer source edit and its relevant local check result (or the exact tooling blocker). When creating a model, follow it with its working renderer. A new plan, task status, decision document or percentage is not implementation progress. Report changed paths, executed checks and the next concrete edit.

Routine SDK exploration is still prohibited after that edit. For a real compiler or model/manifest/CMS validation error, resolve it from the supplied supported contract first; only unresolved errors permit the directly relevant declaration/schema lookup. Record and reuse the correction. If the embedded pattern targets a different SDK version, reuse a compatible existing project pattern; otherwise isolate its affected mapping and continue independent work. Do not upgrade or research merely because of a version mismatch.

After model edits, use the recorded generator and [validation checks](../../optimizely-saas-modeling/references/model-validation.md) on current output. Supported-profile preflight, full schema validation and tenant acceptance are different evidence. An unavailable generator/check is a scoped blocker, not a passed check or a reason to restart discovery. No tenant operation is added to a local-only brief.

## Compact checkpoint

Use an existing task-scoped evidence directory; default to `migration/implementation/<task-key>/checkpoint.json` in the repository. A local descriptive task key is a path label, not an invented Kajoo ID. The following are checkpoint fields, not tool arguments:

| Field | Record |
|---|---|
| `entry` | `implementation-only`, scope, actual decision/message reference and artifact paths/revisions/hashes |
| `repository` | Root/identity, HEAD as provenance, package manifest and lockfile hashes, relevant instruction hash |
| `sdkQualification` | SDK/CLI, Node/package-manager versions; installed resolution matching the lockfile; relevant example/registry/config paths and hashes; inspected API patterns and declaration paths; actual check commands/results |
| `progress` | Changed model/renderer/config paths, completed checks, first edit time, next edit and specific blockers |
| `integration` | Manifest pending/generated/reviewed/blocked; tenant, preview, publish and deploy evidence kept separate |

Preserve the checkpoint across turns and compaction. On resume, read this small record and inspect current changes before consulting references. HEAD is provenance, not a reason to repeat all qualification. New model files or a renderer fix need their type/build checks, not another SDK study.

Requalify only the affected part when SDK/CLI resolution, manifest/lockfile, relevant repository instructions, starter registration/discovery patterns or runtime/toolchain changes; when installed packages no longer match the recorded resolution; or when a new API pattern/actual compiler error is not covered. An approved scope change reopens its design decisions, not unrelated SDK facts. Missing checkpoint means record known facts and the next source action, not perform SDK exploration. During implementation, requalification uses a targeted declaration/schema read only after an actual compiler or model/manifest/CMS validation error identifies the affected API/property; record the correction and reuse it. A changed dependency fingerprint alone does not authorize broad SDK research. Explicitly record what changed and the one check it requires.

## Orchestration and recovery

Orchestrator hands Developer the exact artifact paths, approved slice/decisions, repository, checkpoint path if present, available task ID and local versus tenant authorization. Retrieve any existing pending run before dispatch. When execution is authorized, creating tasks or marking them in progress is followed by actual dispatch in the same turn when available; a directly assigned Developer proceeds with local work. If the user requests create/plan only, save tasks without dispatch and wait.

Prior phase/state reconciliation is outside this entry's critical path. Reuse valid current-project records; leave another project's state untouched and keep a task-scoped checkpoint. Record earlier phases as supplied context or out of scope for this entry, never falsely completed. Later merge legitimate evidence into project state without discarding history. Existing workflow phase dependencies describe the full migration; create/reuse a phase-3 implementation track with only real dependencies of the requested slice instead of waiting on unrelated preparation tasks. Do not bypass a genuine same-scope code/data dependency.

Read a supplied artifact again only when it changes or a specific unresolved field requires it. Search known evidence paths first if it is missing; use a narrow history lookup only to recover the missing path or decision. Once found, save the reference and stop reconstructing it. Tenant/host readiness and broad acceptance references are loaded when those operations become eligible. If repeated reads produce no new fact, return to the recorded next edit or name the concrete blocker.

## Consume a handoff by slice

When assigned a component document, consume its selected block/occurrence, approval provenance and embedded qualified SDK pattern. If only an index is supplied, use it once to resolve the component path and persist that path; do not load all linked shared files. Read a shared section only when its documented trigger applies. Exact linked existing model decisions satisfy the contract without template conversion. The [handoff authoring guide](../../website-visual-qa/references/implementation-handoff.md) is for creating or revising documentation, not a mandatory read before implementation. Fill only a missing decision that changes the next edit; continue unaffected work.

For an existing unchanged model and a renderer-only request, start with the renderer edit and focused check; the first-model step applies when model creation/change is needed. Preserve qualification and model approval for spacing/content-only changes. Use the [operation routing](execution-efficiency.md) when deciding which references or checks are relevant.

## Bounded startup and resume

The component document is the startup packet, not an invitation to reconstruct the whole project. Target 1,000–1,500 estimated tokens total for the component document plus any essential shared excerpts loaded before the first source edit. Count the total, not each file separately. This is a working authoring target, not a runtime guarantee: system/repository instructions, skills, code and tool output also consume context. A reported 4,000-token summarization fallback is not a verified deployed limit. Preserve complete requirements in conditional supporting sections rather than silently dropping them.

Use the document's verified installed-SDK imports/pattern, registration path, first source file/action and exact local check command. A version alone is not qualification. If no valid pattern is recorded, reuse the relevant existing project source pattern; report a specific modeling conflict if that is insufficient and continue independent work. Do not invent unsupported syntax. Run the installed compiler after the first source edit; executing the compiler is allowed and does not authorize dependency browsing. Only an actual SDK API/type compiler error or model/manifest/CMS validation error permits reading the directly relevant declaration or official schema. Record error, correction and reference, then edit/recheck; do not expand to SDK internals. A passing check of the unchanged template is not the first implementation milestone.

On compaction, resume from the small checkpoint: active task, assigned document, completed checks, resolved blockers, changed source files, next source edit and unresolved blockers. Prefer bounded section reads. Do not reread raw conversation history to rebuild already recorded facts. A tool size error requires a smaller relevant excerpt, not retries over the same oversized range. When actual history recovery is necessary, inspect its schema and read the correct message field; never treat summarizer instructions as the user's task.

Classify each gap: blocks a specific coding decision; blocks final visual/behavior acceptance only; or out of scope. Missing exact color/asset mapping need not prevent independent typed structure, but do not invent values or claim fidelity. An unknown SDK property blocks that property's dependent edit only. Continue unaffected work. Record checks not run and why.

For a local-only brief excluding tenant sync/publication/deployment, omit those operations and tenant fixtures from the task's next actions. Keep local representative content only when authorized and clearly labeled. Do not escalate excluded operations into prerequisites for local completion.

## Implementation continuity
The assigned component, shared-foundation or page-assembly document is the sole mandatory handoff read for that unit. Repository instructions still apply. Consult supporting sections only to answer a named question needed for the next edit. Reuse unchanged material already in context; do not create scratch copies solely to read them again or demand fresh full outputs already obtained.
After necessary initial reads, make the first coherent source change and run the relevant local check. For foundation work this may be layout/adapter/registry wiring; do not create an unrelated model merely to satisfy a model-first instruction. Preserve per-component model documents and all model-validation safeguards.
After summarization or restart, use the compact checkpoint and inspect current affected source once. Resume its next action, rather than replaying preparation. A missing checkpoint permits one targeted state reconstruction, not a recurring audit. Recheck successful setup only for an actual failure or relevant environment change. Changed code still needs fresh checks.
If preparation cannot reach an edit, state the exact missing decision and affected operation; continue independent work. Repeated reads do not count as implementation progress.

## Manual task selection
Implementation runs only for task IDs explicitly started by the user. Task 2.5 recommends prerequisites and parallel groups only. Completion, eligibility, phase start or result retrieval never automatically starts another implementation task. Return results and updated readiness; wait for the user to start the next task(s). Preserve the primary per-component handoff and all existing validation and approval safeguards.
