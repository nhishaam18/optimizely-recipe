# Select work and reuse evidence

Use this reference when coordinating mixed requests or diagnosing repeated preparation. Its table is a routing aid, not a checklist to run for every task. Match the next requested deliverable first.

| Request | Read now | First useful output |
|---|---|---|
| Explain a concept / answer a question | Relevant topic only | Direct answer; no handoff, phase tasks or SDK preflight |
| Document annotated screenshots | Supplied evidence + handoff authoring guide | QA visual contract; Developer model decisions/proposals |
| Implement approved section | Assigned component document + conditional shared headings; checkpoint on resume | First required model edit/type check, then renderer |
| Fix CTA spacing / renderer defect | Defect evidence + affected renderer/token rule | Source fix and focused check; unchanged models need no rewrite |
| Add a field / new SDK API pattern | Affected approved type + supplied/source pattern; relevant declaration only after an SDK API/type compiler error or model/manifest/CMS validation error | Scoped model/renderer change and qualification update |
| Synchronize / publish / deploy | Reviewed manifest, current target readback and applicable operation guide | Authorized scoped operation and actual result |
| Independently accept work | Approved criteria + delivered evidence + relevant QA procedure | Measured pass/fail/blocked results |

## Read and execute in bounded units

Batch independent repository reads and searches around the selected slice. Reuse observed paths; follow a reference only to resolve a concrete missing fact. A skill's reference table is a menu, not a reading sequence. If the current context already contains an unchanged reference, use it. Installed declarations settle version-specific syntax; a new compile error justifies a targeted lookup, not a fresh template comparison. Preserve SDK family and dependency fingerprints.

Store one authoritative contract per type/token and occurrence deltas, not duplicate model descriptions in every task. On resume, read the small checkpoint and current diff, then act on its next edit. Update the checkpoint after a meaningful edit/check or before yielding; don't rewrite every artifact after each tool call. No fixed tool-call or elapsed-time budget can substitute for resolving a real dependency.

Use existing local scripts. Type-check the first changed model before extending the pattern; group subsequent independent units using that verified pattern and run appropriate checks after meaningful batches. Re-run checks when inputs change, failures require it or a broader integration stage becomes eligible. Manifest review before tenant sync, actual tenant readback, deployment evidence and independent QA remain required at their operations. A passing cached check is not proof for changed code.

## Compact dispatch and result

Dispatch includes actual task/project IDs, requested deliverable, selected block/occurrence, artifact paths with revisions/anchors, approved decisions and unresolved blockers, repository/checkpoint, allowed actions/destination, and acceptance criteria. Include a small excerpt only if the receiving agent cannot access the artifact; label missing access explicitly. Do not replace the source contract with a lossy summary or copy the entire skill library.

One pending run has one persisted run ID. Retrieve it rather than dispatch another. Independent QA discovery and repository qualification may overlap when neither requires the other's output; model decisions dependent on evidence wait for that evidence. Keep concurrent edits in distinct files and reconcile shared contracts before code consumers proceed. Direct Developer assignments execute locally without manufacturing extra delegation.

Return changed paths, executed check results, new evidence/checkpoint reference, blocked operations and next edit. Report first source edit/check timestamps and preparation/read counts when the runtime exposes them. Compare equivalent workloads before claiming a speed improvement; fewer words and synthetic scenarios only establish reduced input and expected behavior.

## Implementation continuity
The assigned component, shared-foundation or page-assembly document is the sole mandatory handoff read for that unit. Repository instructions still apply. Consult supporting sections only to answer a named question needed for the next edit. Reuse unchanged material already in context; do not create scratch copies solely to read them again or demand fresh full outputs already obtained.
After necessary initial reads, make the first coherent source change and run the relevant local check. For foundation work this may be layout/adapter/registry wiring; do not create an unrelated model merely to satisfy a model-first instruction. Preserve per-component model documents and all model-validation safeguards.
After summarization or restart, use the compact checkpoint and inspect current affected source once. Resume its next action, rather than replaying preparation. A missing checkpoint permits one targeted state reconstruction, not a recurring audit. Recheck successful setup only for an actual failure or relevant environment change. Changed code still needs fresh checks.
If preparation cannot reach an edit, state the exact missing decision and affected operation; continue independent work. Repeated reads do not count as implementation progress.

## Manual task selection
Implementation runs only for task IDs explicitly started by the user. Task 2.5 recommends prerequisites and parallel groups only. Completion, eligibility, phase start or result retrieval never automatically starts another implementation task. Return results and updated readiness; wait for the user to start the next task(s). Preserve the primary per-component handoff and all existing validation and approval safeguards.
