# Visual and content-model implementation handoff

Create or revise a handoff when asked to document annotated screenshots, during new discovery/model design, or when an approved requirement changes. For implementation, consume the existing approved slice directly. For a spacing defect or unrelated question, skip handoff authoring. Existing approved documents satisfy this contract without conversion; missing this template is never a reason to restart discovery or delay an otherwise specified edit.

## Ownership and sequence

QA owns source observations, screenshot annotations, responsive evidence and independent acceptance criteria. Developer owns model/type/property proposals, ownership, references, presentation choices, renderer mappings and installed SDK verification. Orchestrator records the actual approval reference and scope. QA may record proposed mappings but cannot turn a screenshot into an approved CMS schema. Populate one shared revision rather than send separate conflicting specifications.

1. QA joins existing capture evidence and requirements by `blockId` and `occurrenceId`. Preserve original screenshot hashes, coordinate units, viewport/DPR and annotation IDs. Screenshot pixels are not CSS pixels without the scale relationship. Unknown viewport, font, breakpoint or interaction remains unknown or explicitly inferred; give confidence and a verification step.
2. Developer adds the semantic model inventory and complete property contracts. Use the [migration contract](../../optimizely-saas-modeling/references/migration-contract.md) for a new modeling decision. Existing approved models supply these decisions. Keep semantic types, SDK declarations, management payloads and delivered query shapes distinct. An unqualified SDK mapping is pending qualification, not guessed syntax and not a blocker to recording semantic design.
3. Orchestrator binds evidence, model and acceptance to one revision or existing approval. A draft may be documented without approval. Implementation uses approved decisions or explicitly authorized assumptions; unresolved decisions block only dependent work. The handoff does not authorize publication, tenant writes or deployment.
4. Only in authorized implementation mode after the handoff approval and explicit start, Developer reads the assigned component document as the sole mandatory handoff read, including embedded approval provenance and the verified SDK pattern. Shared files are conditional exact-heading references, not a required startup list. Repository instructions and relevant local code still apply. Write/type-check the first required model and implement its renderer under the existing implementation-only entry. If the model already exists unchanged, start the renderer fix. Manifest review remains after code and before tenant synchronization.

## Artifact shape

Use the [template](../assets/implementation-handoff.template.md) when creating a new document; consult the [worked example](handoff-example.md) only if its shape is unclear. Completed copies belong in project evidence. A compact handoff contains:

- An index: revision/status, approved scope and message reference, source/model/token artifact paths and immutable revisions/hashes, section anchors, ownership and next implementation slice.
- Shared model/type definitions and design tokens written once. Per-route occurrences refer to them and record only content/ownership/visual differences. Definition reuse does not imply shared CMS instances.
- A contract per semantic block: annotation-to-element mapping, layout/typography/media, desktop/mobile and intermediate behavior, interactions, accessibility and empty states; type/renderer/config paths and delivery fields; required properties, localization, defaults, validation, ownership, reference constraints and enforcement evidence; measurable acceptance.
- A scoped decision/delta list: observed versus inferred versus approved status, affected consumers, missing input and its actual blocked operation. One unrelated open question does not make the whole document unusable.

For multiple reusable components, create `index.md`, shared model/token documents and one component document per reusable component; group its occurrences and variants. Use the [component template](../assets/component-handoff.template.md). A genuinely single-component request may use one document. The index/full original handoff/approval records are provenance/reference only for assigned implementation, not startup reading. Preserve existing project paths. Do not maintain duplicate Markdown/JSON copies of the same contract; a machine-readable file is optional when actual tooling consumes it. Avoid copying whole capture logs, SDK manuals or generated manifests into the handoff.

## Completeness without a new startup gate

During preparation, select the [supported modeling contract](../../optimizely-saas-modeling/references/supported-model-contract.md) for the actual installed SDK/CLI and embed the component's relevant subset. Record compatibility and exact generation/validation commands. Do not make the entire rulebook or its external sources mandatory implementation reads. Each property needs supported option placement, item definitions, semantic ownership, default/enforcement location and delivered-to-renderer mapping. Prepare a compatible project pattern or isolate the unresolved mapping when package versions differ. Compilation, supported-profile preflight, full schema validation and real CMS evidence are separate acceptance levels.

For a new handoff, check that every approved occurrence resolves to evidence, content type/instance policy, properties, renderer and acceptance criteria. Each property records semantic type, SDK mapping/checkpoint or explicit pending status, required/localized/default, cardinality/validation, embedded versus referenced ownership, allowed target types, delivery field/nullability and enforcement location/status. Supporting types/contracts receive their own property tables. Separate display settings from content. Composition records allowed types, cardinality, nesting, ordering and actual enforcement; do not promise unsupported editor locks.

Include an illustrative fixture or exact content source. It is not a tenant payload, schema validation result or proof of integration. Required image alt behavior and link behavior must be explicit, including intentional decorative images and external links when applicable.

During implementation, check only fields needed by the current edit. If a field is absent, resolve it from the exact linked approved model; ask about a concrete contradiction only when it changes that edit. Do not generate missing paperwork for already specified work. SDK qualification is technical evidence, not a second design approval.

## Changes and reuse

Record source/model/token revisions in the checkpoint. On resume read its next edit and changed scope; reopen documents only for changed inputs or unresolved fields. A content change updates its occurrence/fixture. A shared token change lists its consumers for retest. A new model property updates that type, delivery/renderer mapping and affected checks. A package/API change invalidates the affected qualification. A renderer-only spacing fix preserves model decisions and SDK facts. Preserve previous evidence and scoped approvals; never label a materially changed contract approved using an old message.

## Use measured style evidence selectively

When live-source measurements are missing, QA uses [style extraction](style-extraction.md) in the same capture session, then links relevant sample IDs/crops/coverage to annotations. Developer reviews exact-value token candidates against the existing design system before choosing semantic tokens. Keep unresolved or unstable samples labeled; link evidence rather than copying full DOM/CSS dumps into each section. Skip extraction when current approved evidence already supplies the requested slice. Measured CSS does not approve a model or establish hidden editorial behavior.

## Compact component handoff contract

Put complete current-component decisions in its document: IDs/occurrences, scope, approval provenance, repository and target files, evidence references, models/supporting property contracts, ownership/validation/defaults/editorial controls, visual behavior, acceptance and first source action. Include a minimal verified installed-SDK model/renderer pattern with imports, registration/discovery location, check command and qualification fingerprint. Do not invent a runnable snippet when qualification is pending: record the unresolved decision and independent work. Resolve mappings during handoff preparation; do not send implementation into SDK research. During implementation, write/type-check from supplied patterns; only an actual SDK API/type compiler error or model/manifest/CMS validation error permits the directly relevant declaration or official schema lookup. Reuse recorded qualification when unchanged.

Target 1,000–1,500 estimated tokens for the entire initial packet including essential shared excerpts, not for every file individually. Put supporting detail in conditional files without dropping requirements. Each shared reference names an exact heading, what it supplies and the observable condition requiring it. Keep raw CSS/DOM, screenshots and logs as links; store measured values relevant to this component directly. Index and approval documents are not extra mandatory reads.

Classify gaps as coding blockers, visual/behavior acceptance blockers or out-of-scope, each with affected operation and permitted next action. Preserve unknowns and distinguish observed source behavior from proposed CMS behavior. Existing approved content may be reorganized without reopening approval; record source revision/hash and do not silently change requirements. Record compact resume state incrementally after each component or meaningful edit, not by replaying full conversation history. For local-only briefs omit tenant sync, tenant fixture creation, publishing and deployment actions from the handoff, tasks and progress next steps.

## Version identity

Recipe/skills release versions (for example 1.3.6 or 1.3.7) are independent of Optimizely SDK and CLI package versions. Never compare them or raise a compatibility blocker from their numeric difference. Record recipeVersion separately from sdkPackage/sdkResolvedVersion and cliPackage/cliResolvedVersion, using repository dependency records during preparation. During implementation reuse the recorded versions; package fingerprinting is not an exception to the prohibition on routine node_modules reading. A fingerprint records provenance, not proof of compatibility. Reuse qualified repository patterns. A concrete unsupported API, property or validation error can block its affected operation; a different recipe number cannot. A pattern verified against SDK 3 is not automatically verified against SDK 2 either. Record the exact affected mapping, evidence and independent next action instead of a blanket version blocker. No dependency upgrade or broad SDK exploration follows from a version difference.

## Requiredness mapping

Document component presence separately from required child fields. Do not emit isRequired on a component property. A child-field constraint does not by itself establish parent presence. Preserve approved intent, shared consumers and exact enforcement/coverage gaps.

## Complete annotation-to-model coverage

Apply [component/element coverage](component-annotation.md#carry-forward-into-phase-2). Every approved element ID or explicit occurrence field set must map to model.property, presentation/behavior-only rationale or an unresolved decision. Preserve exact observed copy, action ownership, variant differences and evidence. Reusable definitions/collections do not imply globally shared instances. Put this reconciliation in the existing component handoff; no additional mandatory implementation read. Approval checks mapping coverage; a token target cannot justify omitted elements.


Component localization safeguard: on a property with type `component`, omit `isLocalized` entirely, including false. Apply approved localization to supported individual fields on the referenced component type; do not blanket-localize every child or alter shared consumers without reviewing their semantics. Component array items also cannot carry this metadata. Keep valid array-container metadata distinct from item metadata, and do not apply this prohibition to `contentReference` or scalar properties. Include the choice in each component handoff. During Phase 2 write definitions/examples in the handoff only; application changes belong to authorized implementation. Check the generated manifest with the scoped preflight before any separately authorized tenant sync. Do not initiate a push or routine SDK lookup to check this rule. TypeScript success and preflight success do not prove full CMS acceptance.

Recipe 1.5.0 review format: use [review documents](review-documents.md) and the current component/page templates. Put readable summary and field meanings first, then technical implementation detail. Phase 2 produces documents only; first source action is a future Phase 3 instruction. CMS composition review belongs to Optimizely Specialist.

## Foundation and component separation
Produce one readable model/handoff Markdown file per reusable component, grouping its occurrences and variants. Preserve complete fields, types, validation, editorial controls, UI/style mappings and acceptance criteria. Do not merge component contracts into the foundation document.
Also produce a focused [foundation handoff](../assets/foundation-handoff.template.md) from approved architecture for shared layout, registry, adapters, preview and style loading. Resolve repository/tool commands from setup and actual source patterns. Include one first source action/check and classify blocking, visual and tenant gaps. Page assembly retains its own handoff. Put approval provenance in each primary handoff; original reports/index/approvals are conditional reference material. Phase 2 writes these documents only, never application source.

## Visual fidelity contract
Use one current source baseline per route/device/state with capture hash, browser/viewport/DPR, consent, fonts, image readiness and scroll/interaction state. Preserve superseded revisions; never infer that a new live visit matches an old capture. Missing selectors mean incomplete evidence, not absent content. Reconcile pixels, element and ancestor styles, pseudo-elements, backgrounds, intrinsic assets and clipping before prescribing a disputed layout. DOM presence or bounding boxes do not prove painted visibility. Keep observed appearance, implementation inference and approved target separate.
Each component's primary Markdown handoff contains a concise visual contract: anatomy and reading order, container/full-bleed behavior, grid, typography and wrapping, spacing, imagery/crop, CTA placement, clipping/states, evidence links, agreed tolerances and known gaps. Exact values come from this project's source, never a previous website. Put source-equivalent approved text and assets in fixtures early; keep fixture provenance in data attributes or a separate review panel outside the comparison area. Approve missing-font/asset substitutions and their impact explicitly; missing evidence may block visual acceptance without blocking independent code.
Resolve fonts and content first, then structure/geometry, then fine styling. Implement component anatomy and CSS together. Prefer fixing the responsible rule over piling on overrides; shared CSS changes require consumer retests. Keep semantic DOM order and keyboard order coherent. Verify each component in intended page context and then the assembled page. Use source/target crops plus full-page context, overlays/diffs and measured deltas; align section-relative measurements for local defects and page-level measurements for assembly. Do not rescale images to hide differences or turn all measured heights into fixed CSS heights. Preserve content resilience and requested responsive scope.
QA compares the actual render to authoritative source evidence independently, not just the correction spec. Record technical, visual and CMS/editor status separately (pass, fail, blocked or accepted exception with scope). HTTP 200, build success, populated image src and correct DOM order are not visual acceptance. Inspect actual image decoding and fonts. A changed spec needs traced evidence and invalidation of affected checks; an old QA pass does not override contrary evidence. After two unsuccessful attempts on the same defect, stop speculative patching and perform focused evidence diagnosis before another edit.
Batch related edits; inspect affected rendered sections before repeating full builds. Run code checks appropriate to changes and final integration validation. Reuse unchanged captures/tool paths/SDK qualification. Do not regenerate documentation or broadly read SDK internals for visual defects. Manual task starts and external approval boundaries remain in force.
