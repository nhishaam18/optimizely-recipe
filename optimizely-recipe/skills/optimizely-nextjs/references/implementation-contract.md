# Implementation contract and evidence

For recipe 1.5.0, the five-phase workflow and operation-contract take precedence. This document is conditional background, not an additional task sequence or authorization.
Developer follows this sequence with Orchestrator's recorded scope; QA independently tests the resulting deployment. Optimizely Specialist also participates and owns CMS configuration and approved tenant batches; Developer owns code. For an explicit implementation request, use [implementation-only entry](../../optimizely-migration-workflow/references/implementation-entry.md) and supplied approvals. Use `optimizely-saas-modeling` for architecture, CMS definitions, management writes and content lifecycle.

| Stage | Required artifact/result | Advance condition |
|---|---|---|
| Repository | Existing SDK checkpoint reused/recorded; for new projects, `starter-qualification.md` evaluates published Stride | Installed API pattern for the next edit established; full build evidence follows implementation |
| Evidence/model | Source occurrence/requirement map, field/ownership contract, approved sections and tokens | One recorded review revision; unresolved constraints explicitly owned |
| Local first unit | Approved model source and type-check result, renderer/registries, discovery config and fixture/route | Actual changed files and local checks; manifest generation/review follows model code |
| Tenant representative path | [Hero walkthrough](block-walkthrough.md), reviewed manifest, schema diff/readback, real content IDs and delivery query | Authorized synchronization; actual CMS-driven rendering and bounded composition |
| Preview | Preview route/config, overlay tests, draft isolation evidence | Authorized editor changes/reordering visible without public draft leakage |
| Release | Host runbook, build output, release receipt and two recovery plans | Actual authorized deployment with identifiable URL/version |
| Acceptance | Independent QA report for deployed routes and editorial/publication loop | Pass/fail/blocked/excluded checks recorded; fixes retested |

Maintain the durable chain `source occurrence → requirement → CMS type/content key → SDK selection/query → renderer → deployed route → QA check`. The official SDK can generate selections from registered models; an existing GraphQL/codegen integration can use checked-in fragments. Do not force either mechanism on the other SDK.

Use the existing package manager, router and initialization architecture. Keep server-side querying, privileged configuration and registry setup separate from small client interactions. Treat Graph transport failure, GraphQL error, empty result, route collision, unauthorized preview and unknown renderer as distinct outcomes. Bound query expansion, pagination, retry count and timeouts based on project requirements; HTTP 200 is not enough to establish delivery success.

Composition preserves stable identities and stored order. Renderer reuse and shared content identity are separate decisions. The approved section catalogue needs tenant/editor enforcement evidence, not just React mappings. Display settings select implemented variants; semantic content stays in fields. Use [official-sdk.md](official-sdk.md), [rendering.md](rendering.md), [preview.md](preview.md) and [deployment.md](deployment.md) at those boundaries.

Recipe 1.5.0: intake records intended destinations and scope, not approval of unseen external changes. Require the concrete user-approved batch for schema/content/application writes, uploads, publication and deployment. Reuse that decision only for unchanged scope/destination/revision/effects; material changes need approval again. Developer owns code/host release, Optimizely Specialist owns CMS actions, QA independently verifies, and Orchestrator coordinates actual decisions. Follow the operation-contract rather than broad intake authorization.

Completion claims must state the level actually evidenced: source-checked documentation, locally built frontend, tenant-connected implementation, deployed implementation or independently accepted migration. Missing environment access remains a blocked check. A mock response, screenshot helper success or a dry run cannot be promoted to an integration pass.

## Code-first evidence

For a new project, repository qualification includes [project structure/setup](project-setup.md); existing projects reuse scoped qualification. Model approval covers semantic fields, stable identities, property/contract and composition decisions. Exported definitions, `.mjs` discovery and a generated manifest are implementation outputs. Write/type-check the first model, add its renderer/discovery, then generate/review the manifest before authorized tenant synchronization. Keep bootstrap/application/locale changes and tenant readback separate. Use the workflow model-decision template incrementally as evidence becomes available.

## Model validation evidence

After changing model source, generate current output and run the selected [model checks](../../optimizely-saas-modeling/references/model-validation.md). Record generator/profile/schema identity, output hash, coverage and exact failures. Verify discovery/export keys and registry mapping separately. Fixtures must use the documented renderer shape; real CMS data still needs reference/asset and nullability verification. A renderer-only correction with unchanged models does not reopen SDK qualification or model validation.

## Implementation continuity
The assigned component, shared-foundation or page-assembly document is the sole mandatory handoff read for that unit. Repository instructions still apply. Consult supporting sections only to answer a named question needed for the next edit. Reuse unchanged material already in context; do not create scratch copies solely to read them again or demand fresh full outputs already obtained.
After necessary initial reads, make the first coherent source change and run the relevant local check. For foundation work this may be layout/adapter/registry wiring; do not create an unrelated model merely to satisfy a model-first instruction. Preserve per-component model documents and all model-validation safeguards.
After summarization or restart, use the compact checkpoint and inspect current affected source once. Resume its next action, rather than replaying preparation. A missing checkpoint permits one targeted state reconstruction, not a recurring audit. Recheck successful setup only for an actual failure or relevant environment change. Changed code still needs fresh checks.
If preparation cannot reach an edit, state the exact missing decision and affected operation; continue independent work. Repeated reads do not count as implementation progress.

## Manual task selection
Implementation runs only for task IDs explicitly started by the user. Task 2.5 recommends prerequisites and parallel groups only. Completion, eligibility, phase start or result retrieval never automatically starts another implementation task. Return results and updated readiness; wait for the user to start the next task(s). Preserve the primary per-component handoff and all existing validation and approval safeguards.

## Shared rendering and integration qualification
Phase 3 implements CMS-ready models, placement configuration, media dependencies, registered renderers, delivery adapters and preview plumbing as well as visual UI. Local qualification is not proof of tenant/editor acceptance. Use typed, qualified Graph/SDK response shapes or sanitized real responses for contract fixtures; label assumptions. Exercise nested URLs/link labels, media references/binary URL resolution, missing values, display settings and shared content through production adapters. Do not claim exact tenant shape can only be considered after deployment.
Fixture and CMS paths use the same components/styles and normalized rendering model; transport adapters may differ. Place fixtures on an explicit test-only route so a static page cannot shadow the CMS canonical route. Keep production routes derived from the project brief. Propagate authorized draft/version/locale context to shared header/footer and related fetches; prevent shared draft caching. Invalid/expired preview authorization produces a clear diagnostic, never a silent published-only fallback that hides shared drafts. Do not expose tokens in logs/evidence.
After approved schema/assets, Task 4.4 qualifies one representative draft with section selection, media, link and shared chrome using existing appropriate content or a separately approved minimal bootstrap batch. Read back actual responses, reconcile adapters and verify the native CMS iframe edit/refresh path before broad composition in 4.5. This is not implicit permission for extra tenant writes or publication. Register the actual preview host via an approved batch and verify readback; ephemeral hosts require requalification if changed. Empty content and HTTP 200 are not proof. Preserve downloadable local fallback on unavailable Kajoo preview.
Task 4.5 composes remaining approved content only after qualification. Task 5.1 independently compares the actual CMS-driven page to source and verifies picker selection, edits, refresh, references/images and shared regions. Test published delivery separately after its approval. Late code fixes remain possible but must identify the violated contract, update affected evidence and be manually started as implementation tasks; do not disguise planned missing integration as normal styling work.
