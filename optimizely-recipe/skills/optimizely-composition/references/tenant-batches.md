# Controlled tenant operations

1. Resolve actual connection, tenant/environment, application root, locale and existing-resource policy. Inspect types, groups/formats, references, relevant content, assets, permissions and application settings read-only. Record only needed inventory and version/hash, no secrets.
2. Compare proposed models/composition with current state. Classify create/reuse/update, affected consumers, incompatible type/base-type changes, content conversions, reference remapping and publication effects. Do not silently rename/delete or overwrite unrelated resources. Existing SDK source truth must reconcile with actual tenant state.
3. Prepare the [batch](../../optimizely-migration-workflow/assets/approval-batch.template.md) with concrete commands/payloads and previewed effects. Inspect CLI/config behavior: commands named opti-push or dry-run may create content/applications or require authentication. No fake credentials, broad retries or source SDK browsing to force manifest output. If offline generation is unavailable, record that gap; do not fabricate a generated manifest from a hand-written example.
4. Require user approval for each significant batch before applying. Local preflight errors block affected sync; report partial-profile unchecked areas. An agent technical review is not remote-write authorization. Keep schema, asset upload, draft content/application changes, publish and frontend deploy separately scoped. Reuse an unchanged approved batch; materially changed diffs need approval again.
5. Before applying, re-read affected versions or use supported concurrency checks. Save a recoverable snapshot/export for updates where supported. Stop on drift; prepare the new diff. No promise that deleting a newly created type rolls back migrated content.
6. Apply only approved operations. Capture actual CMS/media/content/application IDs and returned versions; read back and compare. Keep a mapping of source asset/component occurrence to CMS identity. On partial failure, preserve receipts, inspect applied state, and retry only unapplied operations with the same intended identity; never blindly replay the whole batch.
7. Upload approved assets using reuse/checksum candidates and confirmed rights. Keep alt text and crop ownership in the model. Draft creation uses uploaded IDs, correct locale, approved routes, references and composition ordering. Author representative actual content; fixtures are not CMS content.
8. Create shared site content and selected variants; compose the approved Experience and blueprints where justified. Validate tree/root and preview settings. Do not publish as a side effect of draft composition. Document draft-only items and publication dependencies.
9. Before release, approve exact build/host and content version set, including required shared blocks/media. Verify publication/readback, route resolution, cache freshness and recovery limits. Host deployment and CMS publication are distinct outcomes; no automatic rollback that destroys content.

Tool capabilities are a runtime prerequisite. Do not add a fictional Optimizely connector marked connected to a recipe. Secure connection setup belongs to intake; a missing operation should report the missing capability and allow independent local work. CMS edits for QA require their own approved draft/test scope.
