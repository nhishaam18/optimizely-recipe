# Editorial architecture and availability

Record these decisions in the page and component handoffs before source implementation. Experiences/Pages are routable content; an Experience adds Visual Builder composition. A section organizes a page; a component definition is reusable code/schema, which does not mean its content instances are globally shared. No A/B experimentation is implied.

| Intended use | Documented choice and proof |
|---|---|
| Direct section in an Experience | Qualify component compositionBehaviors sectionEnabled and verify Add Section in the real tenant |
| Element inside a section | Qualify elementEnabled and verify the correct element picker/context |
| Owned structured child | component property or component array item with an approved concrete target; no independent picker visibility needed |
| Shared site header/footer | CMS-managed shared instances selected by site/application configuration and optional page variant references; shared site layout resolves them in delivery AND preview |
| Repeated starter layout | Experience/section blueprint; record why needed and test a new instance |

Do not enable every component at every level. Preserve semantic nesting; component picker eligibility, child reference constraints and page-tree mayContainTypes are different controls. Display templates offer implemented named variants, not arbitrary CSS fields. Record exact allowed choices, default and fallback. Confirm SDK serialization and target API semantics; do not transplant CMS 13 examples into CMS SaaS.

For a missing component, check in this order: intended placement, actual tenant type key/base type/compositionBehaviors, successful sync/readback, allowed parent/property rules, relevant user permissions/context, renderer registry and discovery. A renderer being registered does not make its CMS type selectable. Do not re-sync all models or change base types to fix a picker without diagnosing the affected mapping.

Shared header/footer policy: one shared default per site or locale policy, optional named variants, page override reference or inherit default. Explain where editors edit these values. Resolve the same references in CMS preview; include draft/version/locale handling in the qualification. Test propagation on two representative consumers and variant isolation within the approved scope. If a second consumer or variant is unavailable, obtain approval for a minimal test consumer or record that check as pending; do not add source routes or tenant content implicitly. Shared instance changes have a publishing lifecycle and affected consumers; do not promise drafts instantly change public pages.

Blueprints copy layouts and instances are detached from the blueprint. Use references to shared content within the intended architecture; a copied inline header is not shared. Blueprints reduce authoring effort but do not establish the shared update policy. CMS SaaS documents blueprint creation via UI or API; use only supported capabilities actually available in this tenant/tooling. Do not infer endpoint names or borrow the different CMS 13 limitation.

Mixed freedom is explicit per region: fixed layout, editable fields, permitted reordering/add/remove, allowed child types, constrained visual variants, and enforcement layer (CMS / renderer / QA). Do not claim an editor restriction is enforced by prose or TypeScript. If native enforcement is unavailable, present alternatives and the exact limitation before approval.

Readability: explain these decisions without SDK jargon first. Preserve separate observed website facts, proposed editing behavior and user-approved design. Credentials and tenant IDs alone are not proof of compatibility.

## Media and CMS readiness contract
Inspect the actual tenant when read access is authorized. Reuse a suitable concrete media type, including built-in ImageMedia where present; create a custom _image/_video/_media-derived type only when absent or justified by approved metadata/extension needs. Base types and abstract contracts are not concrete upload contentType keys. If tenant access is unavailable, record the dependency as unverified; never assume absence or fabricate keys. Define media dependencies before uploads, synchronize the approved schema first and confirm via readback.
Each model handoff records field reference types/allowed types, concrete media dependency, upload container policy, source asset identity, alt/decorative ownership, crop/focal behavior, reuse and locale strategy. Do not invent locale branches unsupported by media. Usage-specific alternative text can belong on the consuming component; choose deliberately. Component reference fields do not upload binary files. Asset batches separately upload/reuse actual files, map returned identities to fields and verify MIME/decode/access in the intended preview and public contexts. Keep rights and substitutions explicit. Diagnose wrong binary URL, reference expansion, authentication, permissions and publication separately; never assume publishing is the only repair for draft media.
Each reusable component also declares intended placement (selectable section, nested component, reference/shared content or layout region), required composition behavior, renderer registration, display-template association/default/settings, media dependencies and preview mapping. Do not make every child section-selectable. Reuse documented qualified patterns; carry decisions into Phase 3 task acceptance instead of deferring them to composition.
Display templates may target base type, content type or node type. Inspect actual association and existing defaults/consumers, propose the scoped diff and verify readback. Never apply blanket isDefault:true or universal 'one per base type' rules; preserve unrelated defaults. No sample template may silently override approved source styling. Validate against the actual API/SDK contract without routine broad SDK reading.
