# Application scenarios and grading

Run these with the old bundle and the candidate in separate fresh contexts. Give the same prompt and synthetic input facts. Keep outputs and a grading record of assertion, pass/fail and exact evidence. Grade success from the response, not from knowing what the author intended. Distinguish guidance directly supported by the bundle from an evaluator's workaround or guess.

## Three-agent release

Exactly Orchestrator, Developer and QA exist. Discovery/model revision and demo tenant/host actions are approved. A Developer run is pending. Ask for next work, owners, dependencies, state, deployed evidence and maintenance placement.

Expected: model/release owned by Developer; existing approval reused; pending run retrieved rather than duplicated; deployment identity and independent deployed QA; editor edit/reorder/preview/publish/freshness proof; maintenance outside runtime. An unavailable specialist dependency fails applicability even if an evaluator proposes a workaround.

## Semantic model

Two routes share navigation but have independently edited Heroes of the same design. One has cards and FAQ. Editors reorder approved sections; a React Button is reused. Ask for four structures, type/instance choices, fields/styles, shared SEO, REST definition, official SDK mapping and verification with no tenant connected.

Expected: shared navigation, independent Hero instances, no automatic CMS Button type, controlled Visual Builder sections, explicit REST required/localized, layer separation, version-bound shared fields and no invented live results. A fixed content area substituted for the requested authoring mode is a mismatch. An asserted editor lock without verified enforcement is a failure.

## Official SDK and deployed QA

Stride source has workspace dependencies; published versions, host and credentials are unknown. Ask for qualification, model/renderer registration, design tokens, preview, freshness, deployment, matched QA and recovery.

Expected: qualify/pin published output, one coherent official SDK path, model and component registries, composition/preview integration, local work versus blocked tenant/host steps, public/draft isolation, deployment receipt and separate frontend/CMS recovery. No fabricated versions or generic build success presented as integration.

## Implementation-only entry and resumption

Use [implementation-only entry](../../optimizely-migration-workflow/references/implementation-entry.md) in these scenarios. Keep the same facts for old/new runs and record the first source edit separately from planning/task/metadata writes.

- Existing repository, installed SDK/CLI, supplied approved model and screenshots, missing tenant, foreign historical migration state: consume named artifacts, preserve foreign state, reuse the supplied SDK pattern, then write/type-check one model without SDK browsing; only an actual SDK API/type compiler error or model/manifest/CMS validation error permits a targeted declaration/schema read. Generate/review the manifest afterward before any synchronization.
- Resume with unchanged qualification inputs and a changed model source: reuse SDK facts, inspect the source diff and rerun affected checks. Changed model/config output needs a fresh manifest; it does not require a fresh starter survey.
- SDK/lockfile changed: detect installed-resolution mismatch and requalify only affected APIs/toolchain; preserve unrelated semantic approvals.
- Runtime plan mode prohibits writes and requires exit approval: request the real exit promptly using the existing plan; wait for the actual decision, then continue. Prior design approval is not runtime exit approval.
- No usable design/source artifacts: use normal intake/discovery for missing semantics rather than inventing an approved model.

Record actual changed paths, check outcomes, reads/tool calls before first edit and elapsed active execution time when replaying in Kajoo. Simulated next-action responses check instruction interpretation only; they do not establish runtime speedup.

## Additional regression cases

- Retry an import after the response was lost: readback/mapping prevents duplicate content.
- One shared field changes: trace impacted consumers and preserve unrelated content.
- Draft preview works but public site stays stale: separate publish, index and cache observations.
- A mobile screenshot matches while the menu cannot be operated by keyboard: fail functional/accessibility acceptance.
- A new model revision changes only Hero ownership: reopen that scope without discarding unrelated approved work.
- Missing Playwright or inaccessible host: record blocked checks, preserve valid completed evidence and continue independent work.

Static checks, simulated agent outputs, local fixtures and real tenant/deployed runs are different validation levels. Keep that distinction in the final report. Repeated runs and broader prompts are needed before drawing reliability or performance conclusions.

## Visual/model handoff and selective execution

Test screenshot-only facts with no approved ownership: QA records observations/inferences; Developer proposes explicit types/properties; no invented approval, measurements, SDK mappings or editor enforcement. Verify property required/localized/default/validation/cardinality/ownership/reference/delivery/enforcement and supporting types are present or explicitly pending.

Test approved handoff plus matching checkpoint: read the selected slice and first source edit/check, without template conversion or repeated background study. Test a one-route CTA spacing defect: affected renderer/token consumers only, unchanged model/SDK qualification retained. Test a new SDK API error: inspect only the affected declarations and update checkpoint. Test an unrelated explanation: no handoff generation or phase tasks. Grade actual selected reads/actions, not copied rules. Compare equivalent scenarios; synthetic responses and word counts do not establish live latency.

## Selective style evidence

Test an annotated live Hero with heading/button child styles, repeated occurrences and desktop/tablet/mobile differences. Require explicit mappings, bounded structure and raw-derived crops. Test missing parts, count mismatch, broken images and extraction limits: preserve available evidence and identify incomplete scope. Test similar colors: exact groups remain separate proposals; no invented token approval. Test approved existing style evidence and screenshot-only input: no mandatory recapture and no fabricated computed CSS.

## 1.3.6 modeling guardrails

Test these outcomes before release:
- Passing TypeScript plus unknown property options, missing array items or misplaced scalar/list constraints: generated-model preflight rejects with paths; agent corrects from the supplied contract.
- Page-owned repeated cards: shared definition, independently owned values; no silent conversion to shared referenced instances.
- Concrete CMS/schema failure despite a passing compiler: narrow unresolved-error recovery is allowed, followed by correction/checkpoint/recheck, without general SDK browsing.
- Installed SDK differs from supplied example: use a matching existing project pattern or isolate the mapping; no silent upgrade or startup research. Continue independent renderer work.
- Local demo lacks generator credentials: report the blocked check, keep implementing; no excluded tenant writes or false validation pass.
- Strong existing schema check exists: preserve it; do not downgrade to the partial bundled preflight.
- Renderer-only fix: no model rewrite, schema requalification or unrelated documentation reading.

Run `node --test` against the bundled modeling-preflight tests. Include passing actual generated output and failing fixtures beyond isList. Scenario review is not live latency measurement.
